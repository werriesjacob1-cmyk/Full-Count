# Live freshness incident — 2026-08-25, onset ~03:29-03:36 UTC

Persisted per the interruption-safety protocol. This is a REAL incident observed
and acted on live during this session, not a retrospective analysis — timestamps
below are as pulled directly from `list_workflow_runs`/`list_workflow_jobs`.

## What happened

- `Dashboard Live Update` (`*/5 * * * *`) last successful run before the gap:
  **run #273, created 03:29:08 UTC**. No further run (scheduled or otherwise)
  appears for this workflow until this incident's manual recovery dispatch below
  — a 40+ minute gap on a 5-minute cron.
- `Live Freshness Watchdog` (`2-59/5 * * * *`) fired for the real first time ever
  at **03:36:09 UTC** (run #1), completed successfully in 9s, correctly found
  `docs/live.json` fresh at that moment (7 min since the last Dashboard Live
  Update commit, inside its 15-min SLA) and correctly no-op'd — see
  `backtest/scheduled_workflow_inventory_2026-08-25.md` for that first-tick
  detail. It did NOT fire again after that single tick — also a 30+ minute gap
  on its own 5-minute cron, discovered while checking on it.
- `Lineup Watch` (`*/10 * * * *`) shows the same pattern independently: run #444
  at 03:08:24 UTC, then a **47.5-minute gap** before run #445 at 03:55:54 UTC.
- `Odds Snapshot` (hourly) and other lower-frequency workflows show no comparable
  anomaly in this window (consistent with their own cadence).
- By the time this was discovered (~04:08 UTC), `docs/live.json`'s `updated_at`
  was `2026-08-25T03:29:31Z` — **~39 minutes stale**, well past the watchdog's
  own 15-minute SLA, while the watchdog itself had gone quiet too.

## What this is (and isn't) evidence for

This looks like the SAME class of incident as the 2026-08-24 23-run cancellation
streak (see `backtest/runtime_profile_2026-08-25.md`), but that incident's root
cause (the sequential `fetch_game_contexts()` MLB-fetch bottleneck) was already
found and fixed in `47a75920`, merged to main before this new gap started. This
new gap happening AFTER that fix, and affecting multiple independently-scheduled
5-10 minute workflows simultaneously (Dashboard Live Update, its own watchdog,
AND Lineup Watch), is real, live, additional evidence for the SEPARATE, secondary
"repo-wide scheduled-workflow congestion" hypothesis already documented in
`backtest/scheduled_workflow_inventory_2026-08-25.md` (≥720 same-branch pushes/day
from workflows on the same ~5-minute rhythm) — this is not proof of cause, but it
is real-time confirmation that gaps recur even with the known single-job
bottleneck fixed, consistent with a GitHub-side scheduled-trigger delivery/
congestion mechanism operating above the level of any one workflow's own runtime.

Not clean proof either way: Lineup Watch recovered on its own (03:55:54) slightly
BEFORE this incident's manual recovery dispatch (below, ~04:08), and Dashboard
Live Update/the watchdog had NOT recovered on their own as of the manual dispatch
— so this is not simply "one thing was stuck and now it's fixed"; it looks like
independent, possibly-correlated stalls with different recovery timing per
workflow. Recorded honestly rather than forced into a single tidy narrative.

idempotent production workflow (dispatched successfully once already this session
for `dashboard-refresh.yml`, see the Weston-fix live verification). A bounded
